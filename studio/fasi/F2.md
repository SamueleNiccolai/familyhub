# F2 — Produzione

Settimane 8-12 · 7 dic 2026 – 10 gen 2027 · stima **34 h** · capacità 44 h (≈11 sessioni): le due settimane di Natale (21/12 e 28/12) sono leggere, una sessione da 4 h

## Obiettivo
L'API live su internet in HTTPS, e una pipeline che a ogni push su `main` builda, testa e deploya da sola. Da qui in poi ogni fase si costruisce su un sistema «in produzione» usato dalla mia famiglia.

## Cosa saprò fare alla fine
- Containerizzare un'app Spring Boot e orchestrare app + DB + reverse proxy con Compose.
- Gestire un piccolo server Linux: SSH, utente, firewall, Docker, dominio, HTTPS.
- Scrivere una pipeline GitHub Actions (CI su PR, CD su `main`) con segreti e registry.
- Lavorare con branch, PR e rebase come in un team.

## Decisione hosting (prima sessione; scriverla in STATO → Decisioni)
Prezzi verificati il 2026-10-19: ricontrollarli qui prima di decidere. Tetto di spesa: 10 €/mese.
- **A) VPS Hetzner** (consigliato; i prezzi sono saliti due volte nel 2026 e il taglio più piccolo a ottobre non era ordinabile): ops vere, nessuna sorpresa; il server resta documentato nel runbook (Terraform arriva in F8, su AWS).
- **B) Gratis**: Render free per l'app (512 MB, spin-down dopo 15 min: JVM con `JAVA_TOOL_OPTIONS=-Xmx256m`), ma il suo Postgres gratuito scade dopo 30 giorni, quindi il DB va altrove. Con B saltano SSH/ufw/Caddy di B2 e il deploy via SSH di B3: scriverlo. Fly.io non ha più un piano gratuito.
- **C) Oracle Cloud Always Free** (ARM, oggi 2 OCPU / 12 GB): gratis, ma Oracle recupera le istanze inattive (CPU, rete e memoria sotto il 20% per 7 giorni), e un'app familiare lo è.
- Dominio: ~10 €/anno, o gratis con DuckDNS. Con B) il dominio lo dà la piattaforma.

## Blocchi di lavoro
### B1 — Immagine (≈6 h)
- [ ] Immagine Docker del backend: `./mvnw spring-boot:build-image` (Buildpacks) oppure Dockerfile multi-stage; utente non root
- [ ] `infra/docker-compose.prod.yml`: `app` + `postgres` + reverse proxy `caddy` (HTTPS automatico), segreti in `.env`
- [ ] Health check: Actuator `/actuator/health` esposto solo nella rete interna di Compose (anticipo minimo di F5); con Buildpacks nell'immagine non c'è curl (vedi Trappole)
### B2 — Server (≈9 h)
- [ ] Server creato, SSH con chiave, utente non root, `ufw` (22, 80, 443), Docker installato
- [ ] Dominio o sottodominio che punta al server; Caddy serve l'API in HTTPS
- [ ] API protetta fino a F4: `basic_auth` di Caddy (o un header condiviso), con le credenziali nell'app via `EXPO_PUBLIC_…` (non è un segreto vero, ma ferma i bot)
- [ ] Deploy manuale: `docker compose pull && docker compose up -d` funziona; l'app sul telefono in 4G usa l'URL pubblico
### B3 — Pipeline (≈15 h)
- [ ] `.github/workflows/ci.yml`: su PR e push → `./mvnw verify` (Testcontainers gira sui runner `ubuntu-latest`), cache Maven via `setup-java`
- [ ] `.github/workflows/deploy.yml`: su push su `main` → build immagine → push su GHCR → SSH sul server → `compose pull && up -d`; segreti in GitHub Secrets
- [ ] Badge della pipeline nel README; branch protection su `main` (CI verde obbligatoria, PR obbligatoria)
- [ ] Da qui ogni task su `feat/<tema>`: una PR con un conflitto risolto con `git rebase`, per saper spiegare merge vs rebase
### B4 — Prima utente (≈4 h)
- [ ] Un familiare aggiunge una voce dal suo telefono senza il mio PC acceso — Android: APK di anteprima (`eas build -p android --profile preview`, con `"android": { "buildType": "apk" }` nel profilo `preview` di `eas.json`; piano gratuito); iPhone: account Expo gratuito del familiare, invitato nella mia organizzazione Expo, più `eas update` (Expo Go apre solo update di progetti propri o dell'organizzazione; compatibilità con l'SDK di Expo Go da verificare) — screenshot in `studio/evidenze/F2-familiare.png`
- [ ] Chiusura fase

## Definition of done
- Push su `main` → in meno di 10 minuti l'API nuova è live in HTTPS (verificato con un cambiamento visibile, es. un campo in più nella risposta).
- `curl https://<dominio>/api/items` senza credenziali → 401; con le credenziali risponde dal server; `docker compose ps` sul server mostra 3 servizi healthy.
- Una PR con CI rossa non si può mergiare.
- Un familiare ha aggiunto una voce dal suo telefono (screenshot in evidenze).

## Teoria just-in-time
- Docker: immagine vs container, layer, volumi, rete di Compose → docs.docker.com «Get started», solo le prime parti.
- Spring Boot reference → «Container Images» (perché `build-image` fa layer sensati).
- GitHub Actions: workflow, job, step, runner, segreti → GitHub Docs «Building and testing Java with Maven», «Publishing Docker images».
- Caddy: quickstart «reverse proxy» (10 minuti: è la sua forza).
- Git: merge vs rebase e conflitti → Pro Git (git-scm.com/book), capitolo «Git Branching», solo le sezioni su merge e rebase.

## Trappole e punti di scoraggiamento
- JVM che si mangia la RAM del VPS: limitare `-Xmx`, aggiungere 1-2 GB di swap.
- CI lenta: cache Maven (`cache: maven` in `setup-java`); Testcontainers sui runner funziona senza setup.
- Chiave SSH o password nei log della pipeline: Secrets, mai `echo`.
- Healthcheck con `curl` su un'immagine Buildpacks: non c'è curl, e nemmeno la shell. Usare il buildpack `paketo-buildpacks/health-checker` (`BP_HEALTH_CHECKER_ENABLED=true`, test `["CMD", "/workspace/health-check"]`) oppure un Dockerfile multi-stage su un'immagine che ha `wget`.
- Qui ci si scoraggia per errori di rete/permessi/DNS: sono tutti già stati visti da tutti. `/bloccato` con il log esatto.
- Natale: le due settimane leggere sono previste. Una sessione da 4 h a settimana, su un pezzo piccolo (badge, README, un test), senza sensi di colpa.
- Non costruire Kubernetes. Un Compose su un server è esattamente quello che fanno moltissime aziende.
